## 🛠️ 技术选型：Pino 或 Winston
在 Node.js 生态中，最推荐使用 **pino**（配合 `pino-roll` 实现日志滚动切分）。

- **为什么选 Pino？** 它是目前 Node.js 社区性能最高的日志库，采用极简的 JSON 结构化输出。在高并发或处理大文件时，它的 CPU 和内存开销极低，且天然支持**敏感字段脱敏（Redaction）**。

## 🚀 核心落地实现

### 第一步：创建中央日志单例 (`src/utils/logger.js`)
利用 Pino 自带的 `redact` 功能，彻底封死 `apiKey` 或图片 base64 字符串意外泄露到日志文件中的安全隐患。

```javascript
import pino from 'pino';

const isProd = process.env.NODE_ENV === 'production';

export const logger = pino({
  level: process.env.LOG_LEVEL || 'info',
  // 🔒 安全熔断：自动将 Payload 内部的敏感/大体积数据替换为 [REDACTED]
  redact: {
    paths: [
      '*.apiKey', 
      '*.api_key', 
      '*.images[*].data', // 过滤掉庞大的 PDF 页面 base64 数据
      '*.records[*].fields.APIKey'
    ],
    censor: '[REDACTED_FOR_SECURITY]'
  },
  // 生产环境输出纯 JSON 用于检索，开发环境可以使用 pino-pretty 漂亮打印
  transport: isProd ? {
    target: 'pino-roll',
    options: {
      file: './logs/docex',
      frequency: 'daily', // 每天切分一个新文件
      size: '10m',       // 单个日志文件超 10MB 自动切分
      mkdir: true
    }
  } : {
    target: 'pino-pretty',
    options: { colorize: true }
  }
});

```

### 第二步：埋点与异常链路拦截

#### 1. 拦截大模型层异常 (`src/services/llmService.js`)
在前面建立的“大模型解析异常恢复机制”的 catch 块中，顺手拉起结构化日志：

```javascript
import { logger } from '../utils/logger.js';

export async function callOpenAI(payload) {
  try {
    // ... 请求逻辑 ...
  } catch (error) {
    logger.error({
      event: 'LLM_EXECUTION_EXCEPTION',
      errorMessage: error.message,
      // 捕获我们在 V2.0 重构中拼死拦截到的残缺数据与 Token 开销
      rawContent: error.rawContent || null,
      tokenUsage: error.tokenUsage || null
    }, '❌ 大模型服务层发生崩溃或坏包');
    
    throw error; // 继续抛出让前端触发降级熔断
  }
}

```

#### 2. 拦截多维表格字段对齐异常 (`src/services/wpsService.js`)
当触发网页端修改表头导致的 `Field not found` 时，把当前的缓存 Schema 和目标映射一并打入日志：

```javascript
export async function pushToWps(issues) {
  try {
    // ... 写入逻辑 ...
  } catch (error) {
    if (error.message.includes('Field not found')) {
      logger.warn({
        event: 'WPS_SCHEMA_MISMATCH',
        baseId: process.env.WPS_BASE_ID,
        errorDetails: error.response?.data || error.message
      }, '⚠️ 检测到云端多维表格表头发生变动，自动触发映射熔断保护');
    } else {
      logger.error({
        event: 'WPS_PUSH_FAILED',
        errorDetails: error.response?.data || error.message
      }, '❌ 推送数据至 WPS 多维表格发生核心失败');
    }
    throw error;
  }
}

```

## 🏁 终期调优建议

1. **别记重复数据：** 系统目前在 Step 3 成功后已经会自动备份一份完整的 `_result.json`（里面包含了干净的隐患字段明细与 Token 开销）。因此，你的 `usage.log` 日志**只需要记录元数据摘要（如文件MD5、条数、耗时、状态）即可**，不需要把几千字的隐患描述再在日志里复制一遍。
2. **设置日志清理策略（TTL）：** 如果开启了滚动日志（`pino-roll`），建议在服务器上挂一个轻量级的 Cron 任务，或者利用其内置参数，**仅保留最近 30 天的日志**，防止随着时间推移把服务器硬盘吃光。
针对你的生产部署展望，你更倾向于让这套日志**仅仅静静地躺在服务器的 logs/ 文件夹里**供你出问题时上机排查，还是希望接入一个轻量级的通知钩子，当遇到 `ERROR` 级别的严重熔断时**直接向你的飞书/钉钉群发送一条报警卡片**？
